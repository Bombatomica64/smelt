Architecture review — Smelt

2026-06-04 · deepening opportunities

Smelt lowers TypeScript/Python through frontend → HIR → MIR → codegen-rust. Each stage already hides behind a small interface (to_hir, lower_hir, emit_source) — the stages are deep. The friction is inside them: dispatch smeared across files, one boundary leaking across many call sites, and the same emission logic written twice.

One handler per stdlib call, 48+ of them, dispatched by a hand-ordered chain in call.rs; the handlers themselves scattered across builder_part10–15.

After — one table, one adapter per family

stdlib registry
lookup(receiver, method) → LoweringRule
String rules
Array rules
Map/Set rules
Date/Intl rules
Math rules
lodash/fp rules

call_expression() = lookup + apply. New op = one table row.

Problem

Adding one stdlib lowering means editing a 200-line ordered if/else and guessing which numbered part the handler belongs in — there is no index.

Solution

A dispatch table keyed by (receiver shape, method) returning a lowering rule; one adapter per stdlib family sits behind it.

Wins

leverage: one seam, N stdlib families locality: a family lives in one place interface shrinks; dispatch becomes data test surface: rule table, not call.rs

Honours an existing rule: CLAUDE.md — "everything must lower through general rules, except test functions." A registry is the general-rule shape; per-call if-branches are the special-casing it warns against.

Problem

Wrapping and casting decisions sit inline in three modules. The boundary between typed and erased values has no single seam — it leaks.

Solution

Route every typed↔erased crossing through one coercion module: callers ask for a value at a type; the adapter decides wrap/cast/guard.

Wins

3 · One expression emitter — stop writing it twice

Before — two emitters, same job

⇅ duplicated logic, fixes diverge ⇅

callback_expr_text — ~1600 lines

Callback bodies render expressions with their own bespoke logic instead of the core operand path.

After — callbacks reuse the core path

expression emitter
operand · field · index · call
function body callback body

closures reuse the same block/terminator renderer

Problem

Callback expression emission (~1600 lines) re-implements field/index/call rendering, and closures re-emit control flow independently — a bug fixed in one path stays in the other.

Solution

Make callback bodies lower into the same operand/expression and block emitter the main function uses, parameterised by the closure's local environment.

Wins

locality: one place renders expressions delete ~1600 duplicated lines leverage: closures inherit every fix

Problem

One impl ModuleBuilder (98 fields) sliced across 18 numbered files by size. Finding where a concern lives means searching all 18; callback logic alone spans 5 parts.

Solution

Regroup the impl blocks into concern-named modules (expressions, types, stdlib, test-framework). The public interface stays to_hir; these are internal seams only.

5 · Make emitted source the test surface

Before — substring assertions

assert!(src.contains("fn main() {"));
assert!(src.contains("let count: f64"));
assert!(src.contains("println!(\"{}\""));

6000+ lines of .contains() across part_1–7. The seam tests cross is a guess about a fragment, not the emitted module.

After — snapshot the whole output

assert_snapshot!(source_for(ts));
__snapshots__/emits_main.snap
← reviewable full Rust module

The seam is the emitted source itself. Refactors update snapshots in one review, not 6000 edits.

Problem

Codegen is verified by thousands of .contains() fragments. The test surface is fuzzy: it pins substrings, not the module Smelt actually emits, and reformatting cascades into mass edits.

Solution

Adopt snapshot testing (insta) for whole-output cases; keep .contains() only where a single invariant is the point.

Wins

test surface: the real emitted module leverage: one review absorbs reformatting regressions show full diff

smelt-codegen-rust/src/tests/part_1–7_tests.rs · mod.rs (source_for)

Trade-off: CLAUDE.md preserves generated-file mtimes for incremental builds — snapshots are test fixtures, not generated crate files, so they don't touch that. But a snapshot pins exact output, so genuinely-nondeterministic emission (ordering) must be sorted first.

A new Rvalue variant must be added in three exhaustive matches; validation also folds definite-assignment into the same pass.

After — operands described once

Rvalue::operands()
one place enumerates inputs
existence check definite assignment

structural validation walks operands generically; liveness is its own pass.

Problem

Structural validation re-matches every Rvalue variant (~900 lines) duplicating shape knowledge that already exists in lowering and codegen, and definite-assignment is interleaved so it can't run independently.

Solution

Give Rvalue a single operand-enumeration; let the existence check walk it generically. Separate definite-assignment into its own pass over the same enumeration.

Wins

locality: operand shape defined once new variant ⇒ fewer match sites passes become composable

smelt-mir/src/validate.rs:206 · validate.rs:1577 · types.rs (Rvalue) · lower.rs:1915

Speculative: an operand-walking trait is leverage only if the existence check is truly mechanical. Where validation needs variant-specific rules it still branches — measure how much of the 900 lines is genuinely generic before committing.

Top recommendation

Start with #2 — concentrate the SmeltUnknown boundary.

It is the deepening with the clearest seam, the smallest blast radius, and a project rule already pointing at it ("SmeltUnknown conversions should be explicit boundary adapters"). The typed↔erased crossing is the one place generated Rust most often goes wrong; pulling wrap/cast/guard behind one coercion module gives every call site the same behaviour and one place to test it. It also clears the ground for #3: once expression emission shares a coercion seam, unifying the duplicated callback emitter is far less risky. Keep #1 as the next deep cut and treat #4 as the post-phase architecture pass the timing rule calls for.
