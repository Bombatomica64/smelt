## Root causes fixed

1. **`loop`-shaped closure body dropped its `return` value**
   (`emitter/list_query.rs`, `emit_closure_block_inner`). A closure whose body is
   a `for`/`while` loop is rendered as a statement `loop { ... }`. A MIR `Return`
   reached inside the loop was emitted as a bare tail expression followed by
   `; break;` (`value; break;`), which (a) mistyped the loop-body block as the
   value's type instead of the required `()` and (b) left the `loop` yielding
   `()`. Fix: thread an `in_loop` flag through closure-block emission; inside a
   loop every MIR `Return` lowers to an explicit `return <value>;` (new
   `emit_closure_return_statement` helper, shared with the former direct-exit
   path). The all-`return` loop then diverges (`!`) and unifies with the
   closure's declared result type. Cleared the deferred "loop-as-expression"
   cluster (cond/overEvery/overSome/bind/bindKey/orderBy_1/… — E0308 187→151).
   Verified end to end: a `firstMatch` fixture compiles and runs
   (`f(2) => Some("two")`, `f(9) => None`).

2. **`Option<ConcreteUnion>` / concrete-union truthiness matched `SmeltUnknown`
   arms against a non-erased value** (`emitter/types.rs`, `optional_truthy_text`
   and `value_truthy_text`). A generated union (`SmeltUnionNNNN`) is not a
   `SmeltUnknown`, so the `Type::Union` case must erase the inner value through
   the union's `IntoSmeltUnknown` boundary adapter
   (`.map(|value| value.into_smelt_unknown())` / `(value).into_smelt_unknown()`)
   before the runtime-narrowing truthiness match. Truthiness is a genuine
   runtime inspection of the tagged value and only a `bool` escapes, so no static
   shape is lost. Cleared truncate.rs (E0308 151→131).

3. **`extract` applied its erased-`SmeltUnknown` primitive match to an
   already-concrete `Option` source** (`emitter/coercion.rs`, `extract`). The
   `Bool`/`Int`/`Float`/`String` arms of `extract_value_text` match directly on
   a `SmeltUnknown` scrutinee. When a caller reaches `extract` with a concrete
   `Option<String>` source and a primitive target (e.g. an array element passed
   to `String(...)`), it now delegates to the general concrete coercion
   `value_at_type`, which unwraps the `Option`. Scoped to primitive targets so
   the iterable-extraction arms (List/Dict), which normalize their source through
   `into_smelt_unknown` first, still accept non-erased sources — this scoping is
   what keeps `erases_optional_list_source_before_iterable_extraction` passing.
   Cleared camelCase_1.rs (E0308 131→121).

4. **`field_access_type` disagreed with `field_access_text` for `String`/`RegExp`
   receivers** (`emitter/call_runtime.rs`). `field_access_text` emits concrete
   typed reads for a `String` receiver (`.length` → `i64`, `.source` → `String`,
   flag fields → `bool`) and a `RegExp` receiver, but `field_access_type`
   returned `Unknown` for both. A caller coercing an optional field read then
   treated the concrete result as an erased `SmeltUnknown`, producing a
   `SmeltUnknown::` match over an `i64` scrutinee. Fix: give `field_access_type`
   matching `String`/`RegExp` arms so the field type and the emitted text agree.
   Cleared the bulk of template.rs (34→11; the "expected `i64`, found
   `SmeltUnknown`" cluster, E0308 121→98).

## Regression tests (`crates/smelt-codegen-rust/src/tests/part_1_tests.rs`)

- `returns_from_loop_shaped_closure_body_use_explicit_return` (fix 1)
- `erases_optional_union_inner_before_truthiness_match` (fix 2)
- `coerces_concrete_optional_source_without_unknown_extraction` (fix 3)

Fix 4 has no dedicated codegen text test: Smelt's optional-chain flow narrowing
folds every minimal `x?.length` fixture to a `.expect()` before the
`optional_field` map path is reached, so the buggy path cannot be triggered from
a small source. It is covered by the whole-crate es-toolkit measurement
(template.rs 34→11, the 20-site `i64`/`SmeltUnknown` cluster eliminated) and the
fix only makes an existing type lookup agree with the already-emitted text.

## Deferred / not in this round

- **orderBy.rs (16)** — `expected String, found SmeltRecord<String, SmeltUnknown>`
  from a nested-path property-key lowering site repeated across test functions;
  a member-access/property-key typing issue, not a coercion bug.
- **clone_1.rs (12)** — RegExp-clone field typing (`reg_exp.source` treated as
  `SmeltUnknown`) plus an `as f64.clone()` precedence artifact; entangled with
  RegExp-class field resolution (overlaps the E0609 lane).
- **template.rs (remaining 11)** — heterogeneous: `while ()` (loop condition
  lowered to `()`), string-concat operand typing, and a few one-off shape
  mismatches.
- Assorted 2–4 site clusters (attemptAsync/retry/cloneDeepWith/xor/zipWith/…)
  are per-function async `Result`-wrapping and generic-instantiation specifics
  rather than broad emitter bugs.

## SmeltUnknown accounting

Fixes 2 and 3 route values through the existing `IntoSmeltUnknown` /
`value_at_type` boundary adapters at genuine dynamic-inspection or coercion
boundaries; no new avoidable erasure is introduced (both *remove* mismatched
`SmeltUnknown` matches applied to concrete values). Fixes 1 and 4 do not touch
`SmeltUnknown`.
