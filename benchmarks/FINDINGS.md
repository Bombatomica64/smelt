# What the benchmarks point at

`RESULTS.md` has the numbers; this file is the analysis behind them. It is written by
hand and is *not* regenerated by `report.py`.

The headline is uncomfortable and worth stating plainly: **on every one of the 32
paired cases, the Rust that Smelt emits is slower than the TypeScript it was emitted
from** — by roughly two to four orders of magnitude, against a JIT that has had
fifteen years of work poured into exactly these array operations. Memory goes the
other way: the generated binary idles at ~3 MiB against Node's ~46 MiB, and holds a
smaller working set on almost every case.

That gap is not a story about Rust. Hand-written Rust doing this work would beat V8
comfortably. It is a story about four specific lowering behaviours, none of which is
library-specific, and all of which are visible directly in the emitted source. They
are listed here worst-first, with the file and line to look at.

---

## 1. Whole-collection clones inside loops turn linear algorithms quadratic

**Where:** `chunk.rs:105` in the generated remeda crate (and the same shape in 39 of
the generated modules).

The TypeScript for `chunk` walks the input once, slicing out `size` elements per
iteration. The emitted Rust is:

```rust
_smelt_tmp_38 = Into::<SmeltList<_>>::into(
    data.clone().iter().skip({ let len = data.clone().len() as i64; ... })
                       .take({ let len = data.clone().len() as i64; ... })
);
```

`data: SmeltList<SmeltUnknown>`, and `SmeltList: Clone` copies the whole backing
`Vec`. So each iteration of a loop that runs `ceil(n / size)` times deep-copies all
`n` elements — three times, because the two `.len()` reads clone as well. For the
benchmark's `chunk(10_000, 7)` that is 1,429 iterations × 10,000 elements: roughly
14 million element copies to do work that needs 10,000.

This is the single largest contributor to the throughput gap, and it explains why the
worst rows are exactly the ones with an inner loop over an input collection (`chunk`,
`zip`, `partition`, `group_by`, `count_by`, `unique_by`).

Nothing about the source demands this. A `.clone()` here is only needed if the
original is used again afterwards; borrowing is the ordinary answer, and it is what a
team writing this by hand would have written without thinking about it.

**This is not the `clone-strategy` setting.** The fixtures do set
`clone-strategy = "aggressive"`, and that was the first suspect, but `CloneStrategy` in
`crates/smelt-transpiler/src/config.rs:156` is marked `#[expect(dead_code)]` and is
never read: the option is parsed and discarded. The clones come from
`operand_text` in `crates/smelt-codegen-rust/src/emitter/core.rs:2033`, which appends
`.clone()` to every `Operand::Copy` read.

Nor is it a missing move: the same match has
`Operand::Move(place) => self.place_text(place)` (core.rs:2037), and
`crates/smelt-mir/src/opt/move_on_last_use.rs` is a real backward-liveness pass, in
the default pipeline, that rewrites `Copy` to `Move` at a local's last use. It cannot
help here for two independent reasons: `data` is a *parameter*, which
`convertible_locals` excludes outright (move_on_last_use.rs:207), and it is live
across loop iterations, so no last-use rewrite could fire on it anyway. The three
clones are receiver reads of `&self` methods, and a move-based fix is structurally
incapable of removing them — the fix has to be borrow-based.

## 2. Self-recursive closures leak everything they capture, on every call

**Where:** `flatten.rs:8`, `:18`, `:73` in the generated es-toolkit crate.

A local recursive function is lowered as a cell holding the closure, which the closure
then captures so it can call itself:

```rust
// line 8  — the cell
let smelt_capture_recursive: Rc<RefCell<Rc<dyn Fn(...)>>> = Rc::new(RefCell::new(...));
// line 18 — the closure captures an Rc to the cell
let smelt_capture_recursive = smelt_capture_recursive.clone();
// line 73 — and the cell is given an Rc to the closure
(*smelt_capture_recursive.borrow_mut()) = _smelt_tmp_10.clone();
```

That is a textbook `Rc` reference cycle. The closure holds the cell alive, the cell
holds the closure alive, and neither refcount ever reaches zero. Every call to
`flatten` therefore leaks the closure *and everything it captured* — including
`smelt_capture_result`, the list the recursion has been accumulating into.

Measured directly, with the rest of the harness held constant:

| Iterations | Peak RSS |
| ---: | ---: |
| 1,153 | 396 MiB |
| 5,601 | 1,779 MiB |

Peak RSS rises linearly with iteration count at ~320 KiB per call and never plateaus.
This was initially mistaken for a workload footprint; it is not. The three runtime
identity tables (`SMELT_LIST_IDENTITIES`, `SMELT_PROMISE_IDENTITIES`,
`SMELT_FUNCTION_ORIGINS`) are all empty on this path, so the retention is the cycle
itself. `benchmarks/rust/smelt_bench_harness.rs::identity_table_sizes` exists to make
that distinction checkable rather than assumed.

The control case is in the same report: remeda's `flat` does not go through this
lowering, and it retains **76 bytes per op** against es-toolkit `flatten`'s 367 KiB —
while running at 4,809 ops/s, within 1.1x of the TypeScript and by far the closest row
in the whole table. Same operation, same harness; the difference is the cycle.

The standard Rust idiom is for the closure's self-reference to be a `Weak`, upgraded
at the call site. A long-running service built from this output would grow without
bound today.

## 3. Module-level `const` non-primitives are rebuilt at every call site, every call

**Where:** `words.rs:8` in the generated es-toolkit crate.

es-toolkit declares its word-splitting pattern once, at module scope:

```ts
export const CASE_SPLIT_PATTERN =
  /\p{Lu}?\p{Ll}+|[0-9]+|\p{Lu}+(?!\p{Ll})|\p{Emoji_Presentation}|.../gu;

export function words(str: string): string[] {
  return Array.from(str.match(CASE_SPLIT_PATTERN) ?? []);
}
```

The emitted Rust inlines the constant into the call site:

```rust
pub(crate) fn words_150(str: String) -> SmeltList<String> {
    let _smelt_tmp_1: SmeltRegExp = SmeltRegExp::new("\\p{Lu}?\\p{Ll}+|...".to_owned(), "gu".to_owned());
    ...
}
```

So a Unicode-property regex is *compiled from source text on every call*. In
JavaScript the `RegExp` is constructed once when the module is evaluated. This is why
`camel_case` and `kebab_case` are among the worst rows in both libraries despite doing
very little else: nearly all of the time is regex compilation, repeated 5,000 times
per op.

Four generated es-toolkit modules construct a `SmeltRegExp` this way. A module-level
`const` whose initializer has construction cost wants to be a lazily-initialized
static, not an inlined expression. (There is an existing note on adjacent behaviour in
`blocker-logs/estk-const-item-inlining.md`.)

## 4. Erasure is expensive, and it is measurable in isolation

The two libraries make different demands on the emitter, and comparing them is
instructive.

**es-toolkit** exports ordinary typed functions, so much of its generated surface is
typed too — `camel_case(String) -> String`, `chunk(SmeltList<SmeltUnknown>, f64)`, and
a family of generic `fn f<T: Clone + Default + IntoSmeltUnknown + SmeltFromUnknown>`.

**remeda** is built on `purry`, a runtime data-first/data-last dispatcher that inspects
`arguments` to work out how it was called. Smelt lowers that faithfully, so every
remeda entry point is `fn(args: SmeltList<SmeltUnknown>) -> Result<SmeltUnknown, _>`.
The arguments are erased because in the source they genuinely are; that is remeda's
API design showing up in the output, not a Smelt choice. It does mean the remeda rows
carry an erasure cost that the es-toolkit rows do not, and the two libraries' tables
should not be read against each other.

Where es-toolkit's generated function is generic, the benchmark measures both
instantiations, which prices erasure with no JavaScript involved on either side:

| Case | Instantiation | ops/s |
| --- | --- | ---: |
| `unique` | `T = SmeltUnknown` (what an erased caller gets) | 12.9 |
| `unique_typed` | `T = f64` (what a caller with a real `number[]` gets) | 19.2 |

**~1.5× throughput, for free, purely from the element type being known.** That is the
`CLAUDE.md` north star measured directly: the generic path is already there, and every
value that reaches it with a concrete type instead of a tag gets that speedup. It also
suggests erasure is *not* the main cost here — findings 1–3 are much larger — so
de-erasing alone would not close the gap.

---

## Where this leaves things

The four findings are independent, and none needs a special case to fix:

1. don't clone a collection inside a loop that iterates it — borrow;
2. break the recursive-closure cycle with `Weak`;
3. hoist module-level `const` initializers with construction cost into lazy statics;
4. keep carrying concrete types down to runtime, which is already the stated direction.

(1) and (3) are pure throughput. (2) is a correctness problem as much as a performance
one — it is an unbounded leak in any generated program that uses a local recursive
function. Ranked by what a user of the output would hit first, (2) is the one to fix.

Everything above is reproducible from a clean checkout with `benchmarks/prepare.py`
followed by `benchmarks/run.py`; the per-case numbers quoted here are in
`benchmarks/results/results.json`.
